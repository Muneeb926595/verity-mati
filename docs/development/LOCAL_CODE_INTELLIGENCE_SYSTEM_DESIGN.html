Verity — a local system that explains how your C & C# code actually behaves

A design for an offline code-intelligence system that combines compiler-grade static analysis, code graphs, sandboxed execution and a local LLM to answer questions like “GPS sends heading = 270 — what exactly happens?”, with file/line evidence and an explicit status on every claim. It is written for the engineers who would build it and the leads deciding whether to. Verity is a working name: the instrument fixes a position by measuring against known references, which is what every answer here has to do.

GENERIC BY DESIGN · 00

The system adapts instead of asking

Verity has to work on any machine and any C or C# codebase without anyone supplying the target chip, the compiler, the toolchain or the hardware. It gets there by detecting what it can, assuming the safest default or sweeping every plausible value for the rest, and putting every assumption on the answer. Optional hints can narrow things down, but they are never required. The rule behind all of it: unknowns become parameters of the answer, never questions for the user.

Detect → assume → label → override
The machine
  • CPU, RAM, GPU vendor and VRAM
  • Host OS and architecture (x64, arm64)
  • Installed tools: compilers, SDKs, .NET SDKs, debuggers, isolation providers
  • → a capability class and a set of platform adapters
The codebase
  • Languages and projects present
  • Build files, if any, and whether they build
  • C dialect signals; C# target framework and UI stack
  • → capture or reconstruct the build, with a fidelity level
The unknowns
  • Target data model (type widths, char signedness)
  • Configuration macros nobody defined
  • Runtime values, timing, indirect targets
  • → swept or parameterised, never asked

Everything else (extractors, fact store, graphs, verifier) is plain CPU code that runs on Windows, Linux and macOS, on x64 and arm64. The manifest is data: when better models appear, update the manifest and re-run the benchmark. No code changes.

3 · Codebase independence: C and C# without being told

C: which compiler dialect?

Every file is scored against a set of dialect packs. These are data files holding predefined macros, keyword and intrinsic shims, pragma handling and a candidate data model. Every file is always parsed with the neutral pack, and the best-scoring vendor pack is added when its score clears a threshold. Where the two disagree, both results are kept (cfg_mask) and the difference is shown.

Fidelity levels: how facts were extracted, and the strongest status each allows
  • Every answer states its basis, e.g. “neutral C17 + MSVC pack · F3 · 4 stubbed headers”.
  • Stubbed constants never support value claims.
  • A second, build-free parser. cppcheck (GPL-3.0, run as an external tool) produces a symbol database and possible-value analysis from --dump without a build. When Clang's binding fails but cppcheck and tree-sitter agree on a unique name, the fact is kept as INFERENCE (“name-matched, 2 parsers agree”). Joern is an optional data-flow cross-check.
  • Unknown configuration becomes a parameter. Macros that are tested in #if but never defined (“free macros”) are reported as configuration knobs. The knobs that guard the most code are indexed both ways, so answers read “with USE_EKF: path A; without it: path B”.
  • Absence certificates list stubbed headers and unparsed regions as blind spots.
  • Prior art: PsycheC (BSD-3) infers missing declarations for incomplete C. It's worth evaluating as an alternative or complement to the stub loop.

C: an unknown target (sweep the data models, don't ask for the chip)

Most facts don't depend on the target: what calls what, what's written where, which branch guards what. C: hardware access without a chip database

  • Memory-mapped I/O is recognised by pattern, not by chip: volatile accesses through absolute-address casts (*(volatile uint32_t *)0x40021000), linker-placed volatile struct register overlays and bit-field views (Regs.CTRL.bit.EN = 1), __IO-style macros. Each becomes an I/O site in the catalogue.
  • Interrupt handlers are detected from interrupt keywords and attributes in any dialect pack (CONFIRMED), from function addresses stored in vector-like tables (CONFIRMED once the table is resolved), or from naming conventions such as *_IRQHandler and *_isr (INFERENCE).
  • API knowledge packs (data again) describe what well-known APIs do: spawn threads, register callbacks, perform I/O, queue, lock, arm timers. Win32, POSIX, the C runtime, common RTOS APIs (FreeRTOS, CMSIS-RTOS2, Zephyr, VxWorks, …) and the .NET BCL come bundled. An unknown API is treated as an opaque external, which is safe but less informative.

C#: detected, not configured

  • Target framework comes from .csproj / packages.config when present, otherwise from API usage (System.Windows.Forms, XAML namespaces, ASP.NET types). The matching reference assemblies (Basic.Reference.Assemblies packs cover .NET Framework 4.x through .NET 11, all offline) or installed targeting packs are selected automatically.
  • Missing NuGet packages become error types, and facts that touch them cap at INFERENCE.
  • UI wiring: WinForms handlers come from *.Designer.cs. For XAML stacks (WPF, and similar XAML frameworks), .xaml files are parsed for x:Class, x:Name and event attributes, because the XAML compiler doesn't run in ad-hoc mode.
  • Preprocessor symbols: Debug (DEBUG;TRACE) and Release (TRACE) are both indexed.
  • Interop: P/Invoke edges are extracted when [DllImport] or [LibraryImport] appears. There's nothing to configure.

FRAME · 01

Executive summary

The goal is achievable, but not the way it is usually framed. An LLM will not understand a multi-million-line repository. Compilers can extract the facts, analyses can derive the relationships, and execution can confirm what really happens. The LLM's job is to plan the investigation and explain the result, and a deterministic verifier decides what the user is allowed to see as fact.

v0.3 · generic by design. No target chip, compiler, toolchain or hardware details are needed. The system detects the machine and the codebase, sweeps what it can't detect (data models, configuration macros), labels every assumption on the answer, and accepts optional hints. Only the model depends on hardware: a capability probe and self-benchmark pick a rung on the model ladder, from C0 (no LLM, exact answers only) to C5. Code without a build is reconstructed, and every fact carries a fidelity level. Details are in §00.

The design in one paragraph

Capture the real build (MSBuild for C#, compile_commands.json for C). Run Roslyn and Clang extractors that write typed facts into a local SQLite fact store: symbols, references by role, call edges with resolution kind, CFGs, def-use, config keys, entry points and I/O sites. Derive graphs and program slices from those facts. Add hybrid lexical and embedding search only to get from natural language to candidate symbols. A local LLM drives typed tools through intent-specific recipes, then emits its answer as a ledger of typed claims. A verifier checks every claim against the fact store and runtime traces, and labels it CONFIRMED OBSERVED INFERENCE RUNTIME-DEPENDENT or UNKNOWN. For concrete scenarios (“lat = 33.6844 …”) the system prefers to run the real code in a sandboxed harness and explain the observed trace, using static analysis to show the paths that were not taken.

FRAME · 02

Is the approach sound? Challenging the assumptions

The brief is right about the goal and right to distrust “chatbot over embeddings”. Several of its implicit assumptions still don't hold, and each wrong one would cost months. Here they are with a verdict on each.

“Once the repository is indexed, the LLM will understand it.” Doesn't hold

A local model reads roughly 20–60K tokens at a time. A 2M-line repository is around 25M tokens, a thousand times more. The understanding has to live outside the model, in a fact store and graphs the model queries. The model is a planner and explainer working over tool output. It never holds the system in its head, and it should never be the source of a structural fact.

“The source files are enough to understand the code.” Partly

In C and C#, the build decides what the program is. Preprocessor defines, include paths, the target triple, project references, NuGet packages, source generators and #if symbols can all change which function a call binds to, or whether the code exists at all. Two build configurations are two different programs. The system must capture the build and tag every fact with the configuration it holds for. When there is no build to capture, which is common, the system reconstructs one (compiler profile, include resolution, stubbed headers) and tags every fact with the fidelity it was extracted at (§00).

“Embeddings and a vector database are the retrieval backbone.” Doesn't hold

Similarity search ranks things. It can't enumerate, it has no idea of direction (caller vs callee), and it can't tell heading the field from heading a parameter three files away. Most of your questions (“where is it modified?”, “what calls this?”, “all paths”) need complete, exact answers, and those come from a symbol index and graph traversal. Embeddings earn a narrower role: bridging vocabulary, as in “where does the aircraft decide which way to turn?” → ComputeBankCommand. See §17.

“Static analysis can list all possible execution paths.” Doesn't hold at scale

Path count grows exponentially with branches, loops make it unbounded, and exact reachability is undecidable in general (Rice's theorem). What is feasible, and more useful: (a) path conditions (“M runs only if fix.valid && mode == AUTO”), (b) bounded enumeration inside a program slice, (c) dominance facts (every path to the actuator goes through Validate()). The system must say which of these it produced.

“Static analysis can tell me what happens for lat = 33.6844, heading = 270.” Partly

Static analysis finds which branches depend on the input, and it can fold simple comparisons against constants. It becomes fragile once the data goes through unit and fixed-point conversions (e.g. degrees × 10⁷ stored as int32), stateful filters (Kalman, moving averages), timing (which loop tick consumes the fix) or floating-point edge cases. The reliable method is to execute the real code with that input in a sandboxed harness, record the trace, and have the LLM explain the OBSERVED path. Static analysis then shows the alternatives and why they weren't taken. See §25 and §26.

“Compiler truth > repository evidence > runtime evidence > LLM inference.” Needs refining

A single total order is wrong because the sources answer different kinds of claim. Static analysis is authoritative for what exists and what may happen. Runtime is authoritative for what did happen in a given run, and it is the only thing that confirms an indirect call. Runtime can never prove absence. Static analysis can prove “cannot happen” only when the region has no unresolved indirect calls, reflection or memcpy into the state involved. §24 replaces the total order with a precedence table per claim type.

“A bigger local model gives better answers.” Doesn't hold

In this architecture accuracy comes from the tools. What the model has to do: call tools reliably, emit valid structured output, and reason well over about 30K tokens of dense evidence, fast, because a single answer takes 10–40 model steps. A mid-size mixture-of-experts coder model with small active parameters and good tool calling usually beats a larger dense model that is slower and stuffed with context. The benchmark in §34 decides, not the parameter count.

“Long context windows solve repository scale.” Doesn't hold

Two reasons. Cost: prompt processing on CPU or Apple Silicon runs from tens to a few hundred tokens per second, so a 100K-token prompt can take minutes per step. Quality: retrieval and reasoning over long inputs degrade well before the advertised limit. The design aims for a working context of about 32K and treats context as a budget (§19).

“Language servers (clangd, Roslyn LSP) give us what we need.” Partly

LSPs are built for one interactive request at a time: go-to-definition, find-references, call hierarchy. They aren't built for bulk export, they don't expose CFGs or data flow, and every query is a round trip. We use the compiler APIs directly for indexing. LSPs remain useful as an independent oracle in the benchmark and for editor integration.

“One toolchain can serve C and C#.” Doesn't hold

They are different compilers with different semantic models, failure modes and build systems. tree-sitter parses both, but it resolves nothing: no types, no overloads, no macro expansion. The right structure is two compiler-grade extractors feeding one shared fact schema, plus explicit cross-language edges (P/Invoke, shared message layouts, IPC).

“The LLM can check its own answer.” Doesn't hold

Self-critique by the same model tends to re-confirm its own plausible-sounding mistakes, especially transitive ones (“A calls C” when A actually calls B, which calls C). Verification has to be external and deterministic: look up the edge, re-read the cited lines, check that every identifier in the answer resolves to a real symbol.

“The system can report what is not handled.” Only with a certificate

“I found no handling for GPS loss” is the most valuable answer this system can give and the easiest to get wrong. An absence claim is only as good as the search behind it, so every one carries an absence certificate: what was searched (readers of lastFixTime, timers, exception handlers on the path), and what could hide handling (for example, three unresolved function-pointer calls in nav/).

The division of labour: who is allowed to answer what

The tenets this design commits to

  1. Facts come from compilers and analysers. The LLM never creates a fact. It proposes claims, and claims get checked.
  2. Every answer is a ledger of typed claims, each with evidence and a status. Prose is bound to claims.
  3. Execute when you can, infer when you must, and say “unknown” otherwise.
  4. Completeness questions go to indexes. Fuzzy questions go to search.
  5. Context is a budget. Send slices and symbol cards, not files.
  6. Everything is content-addressed. Stale evidence gets detected, never trusted.
  7. Nothing leaves the machine, enforced by the OS rather than by trusting each tool's config flags.
Knowledge check
Static analysis reports no call path from OnGpsLost() to EnterDeadReckoning(). When can you tell the user “this transition never happens”?
Why: the graph over-approximates the edges it can see and misses the ones it cannot resolve. A “never” is an absence claim, and it needs a coverage certificate that lists the unresolved edges in scope. The LLM agreeing adds nothing.

🧠 Remember

  • The build is part of the program. Capture it when you can; reconstruct it and label the fidelity when you can't.
  • “All paths” means path conditions plus bounded enumeration, not exhaustive listing.
  • Evidence precedence depends on the claim type. Runtime confirms; only static analysis with a certificate can deny.

FRAME · 03

Exact problem definition

Before choosing any tool, pin down what an “answer” is and what it is relative to. Most of the design follows from this definition.

Given a repository snapshot R@v, a set of captured build configurations C = {c₁…cₙ}, an optional execution environment E (test projects, host builds, simulators) and a question q in natural language, optionally with a scenario σ (inputs, faults, timing, configuration overrides),

produce an answer A = ⟨T, K, X⟩: a structured result or ordered trace T; a claim ledger K, where each claim has a type, subject, object, evidence set and status; and an explanation X in which every sentence is bound to claims in K,

so that no CONFIRMED claim is false, relevant facts are recalled, statuses are calibrated, and latency and footprint fit on one workstation with no network.

The unit of truthEvery fact holds relative to a (revision, configuration) pair, and runtime facts also to a run. “ProcessGps calls ApplyEkf” may be true in Release|FEATURE_EKF and false in Debug. The store records this explicitly, and answers mention it when configurations disagree. For code without a build, the “configuration” is a reconstructed compiler profile, and its fidelity level (§00) travels with every fact. When the target is unknown, width-dependent facts also carry the data models they hold for.

FRAME · 05

Non-goals

Deliberately out of scope for v1. Each item was cut because it would pull the design towards a different product, not because it lacks value.

✍️ Not a code generator

No autocomplete, no feature-writing copilot. It may draft harnesses and tests, but only as instruments of analysis.

📜 Not a formal verifier

It can run Frama-C, IKOS or CBMC and report what they find. Its output is engineering insight, not DO-178C or ISO 26262 certification evidence.

🌌 No whole-system symbolic execution

Deep analysis runs on bounded slices, on demand. A whole-program pass wouldn't finish on real repositories.

🛩️ No hardware-in-the-loop

Host builds and emulators (Renode, QEMU) are integration points for later. Real sensors and real-time timing stay out.

👥 Not a team server

Single user, single workstation. A shared on-prem deployment is a future item (§37).

🔤 No languages beyond C and C#

C++ mostly works through the Clang extractor, and VB.NET through Roslyn. Neither is a target, so neither is benchmarked.

🧪 No model training in v1

No fine-tuning on the repository. It risks memorising stale code and doesn't beat retrieval over fresh facts. We revisit once there are verified traces to distil.

🪄 No confident answers without a build

If the build can't be captured, the system still answers, but syntactic facts can't reach CONFIRMED.

Why this shape, and not the obvious alternatives

“RAG chatbot over code”
  • Chunks → embeddings → top-k → LLM

  • Invents call paths that sound plausible

  • Sourcegraph / CodeQL-style queries
  • Precise, but you need to know the query language and the symbol name
  • Can't explain intent or plan a multi-step investigation
  • Kept as the knowledge plane, with the LLM added on top.
This hybrid
  • Compilers for facts, execution for observations
  • LLM for planning and prose only
  • Verifier between the LLM and the user
  • Each component has to earn its place on the benchmark

How it stays fast on huge codebases

  1. The UI never computes. Search, filtering, sorting, graph queries and layout all run in the engine or in Web Workers. The main thread only renders.
  2. Everything streams. Results, progress, tokens and claims arrive as events, and the first visible response comes in milliseconds, not when the whole job finishes.
  3. Everything is virtualised. File trees, caller lists and trace tables render only the rows on screen. The code viewer renders only visible lines and fetches line ranges as you scroll.
  4. Payloads are bounded. The API returns pages (e.g. 200 rows) plus a total count. Large row sets travel as MessagePack, not bulky JSON.
  5. Graphs have a level of detail. Neighbourhoods are never the whole call graph. They render with WebGL, labels hide when zoomed out, and hub nodes collapse.
  6. Interactive work comes first. A new question pauses background jobs (summaries, embeddings) on the GPU and CPU; they resume afterwards. Every job can be cancelled, and a superseded query is cancelled automatically.
  7. Syntax highlighting comes from the engine. tree-sitter already parsed the file, so the UI applies token spans for the visible range instead of re-parsing large files.
  8. Verified claims render progressively. Claims appear one by one as they pass the verifier. Unverified draft prose is never shown as fact; an explicit “show draft” toggle labels it unverified.

They are parallel indexes with different query semantics. Some are exact and complete, some over-approximate, some only rank, and one records what was observed. The agent picks among them per question.

Embedded C: making Clang read vendor dialects

Dialect packsThe shim technique below is packaged as dialect packs: data files detected per file from signals in the source, so nobody has to say which compiler the code was written for (§00). Targets with unusual type widths are handled by the data-model sweep, not by asking for the chip.

If the firmware is built with IAR iccarm, Keil ARMCC 5, TI armcl / cl2000 or GHS, Clang won't accept it as written. The standard workaround works well enough for indexing:

  1. Target: --target=arm-none-eabi -mcpu=… -mthumb -nostdinc plus the vendor's include paths.
  2. Predefined macros: dump them from the vendor compiler (e.g. IAR --predef_macros) and pass them as -D so the same #if branches are taken.
  3. Shim header: -include vendor_shim.h defines away or maps keywords (__interrupt, __no_init, __ramfunc, __irq) and declares intrinsics.
  4. Pre-pass for constructs that aren't C at all: var @ 0x4000 placement and #pragma location get rewritten to attributes, with the original line numbers preserved.
  5. Recovery: -ferror-limit=0. TUs with errors are kept and their error regions flagged (§12).

Arm Compiler 6 (armclang) and TI Arm Clang are Clang-based already, so they are the easy case. Treat vendor project-to-database exporters (IAR -jsondb, CMSIS-Toolbox) as verify on your toolchain version.

Hub suppressionFunctions like log_printf, assert_fail or Logger.Debug have thousands of callers and swamp path enumeration. They are auto-detected by fan-in and excluded from path search by default, and still available on request.
Measuring the graphEvery test run produces observed call edges. Static recall = observed edges that the static graph already had ÷ all observed edges. A miss is either an extractor bug or an unresolved indirect call, and both are actionable. This is the call graph's own quality metric in the benchmark.

🧠 Remember

  • Every edge records its resolution method. Status follows from it.
  • In embedded C, const handler tables resolve most function-pointer calls cheaply and exactly.
  • Threads, queues and events are hops. The link is static; when it fires is runtime.

Where data “originates”: the I/O catalogue

“Origin” is a definite place: the call site where bytes enter the process. The index keeps a catalogue of sources (read, recv, SerialPort.Read / DataReceived, NetworkStream.Read, SocketCAN, HAL UART/SPI/I²C reads, DMA buffers, memory-mapped registers) and sinks (actuator writes, PWM registers, send, displays, logs). Provenance becomes a graph query from a sink back to the sources, answered on the slice.

Deserialisation is data flow too

  • C: memcpy(&pkt, buf, sizeof pkt) into a packed struct is resolved with record-layout byte offsets, so “bytes 8–11 become pkt.lat_e7” is a fact. MAVLink mavlink_msg_*_decode and _get_<field> functions map one-to-one to the XML definitions.
  • C#: [JsonPropertyName] / [DataMember] / protobuf field numbers map wire names to properties. BinaryReader sequences are read in order.
  • Units and scaling (lat_e7 * 1e-7, knots → m/s) are recorded along the slice. Their meaning (“degrees true”) comes from names and comments and is marked INFERENCE.
Why the heavy rungs are on demandWhole-program pointer analysis and abstract interpretation can take hours on millions of lines. Scoped to the slice behind one question, they usually finish in seconds to minutes, and the result is cached under the slice's hash. Slicing also pays for itself as context compression: code-property-graph slicing cut code size by 68–91% while improving LLM vulnerability-detection F1 by 15–40% (LLMxCPG, arXiv 2507.16585).
Soundness holes to report, not hidevoid* context pointers in callbacks, unions, casts, memcpy into shared state, inline assembly, DMA, reflection and serializer magic. When a slice crosses one of these, the answer says so, and absence claims in that region stay uncertified.
License check: SVFSVF (Andersen and flow-sensitive points-to on LLVM IR) is powerful, but its license could not be confirmed from the primary source. Research suggests AGPL-3.0. PhASAR (MIT) is the default, and SVF is an option after legal review.

🧠 Remember

  • The state graph (DF2) answers most “where modified / what depends on it” questions cheaply, with no alias analysis.
  • Value ranges for C come from Frama-C Eva. C# has no equivalent, so use runtime plus property tests.
  • Slices are both the analysis result and the LLM's context.

Why not a graph database

  • Write pattern: facts are replaced one file at a time, transactionally. That's a relational strength.

What the evidence says about embeddings vs search

🔎 Agentic search won in practice

The Claude Code team reported that early RAG over a local vector DB was beaten by agentic search, which was also simpler and avoided staleness and privacy problems (Boris Cherny, 2026). Sourcegraph's Cody Enterprise moved from embeddings to search (Feb 2024).

➕ …but semantic search helps as an add-on

Cursor measured +12.5% average accuracy from adding semantic search on top of grep, with a custom embedder trained on agent sessions (Nov 2025). Hybrid, not either/or.

📉 General embedders degrade on agentic retrieval

CORE-Bench (arXiv 2606.11864) found embedding models drop sharply when moving from classic code search to retrieval for coding agents, and that light fine-tuning helps.

🧭 Agents beat one-shot RAG for repo QA

SWE-QA-Pro (arXiv 2603.16124): 40.67 with an agent vs 27.69 without. DeepRepoQA (arXiv 2608.24221): 64.43 vs 61.13 for function-chunk RAG. The recurring failure is having no structural fallback.

  • Identifier-aware lexical search. The FTS5 tokenizer indexes ProcessGpsData as process gps data processgpsdata, so both “gps data” and the exact name match. Comments and string literals get their own fields.
  • Domain glossary. An LLM-drafted, human-reviewable glossary built from comments and docs (hdg ≈ heading ≈ yaw ≈ course; HDOP; GGA/RMC; EKF; AHRS), each entry with evidence. It is used for query expansion and marked INFERENCE.
  • Fusion by Reciprocal Rank Fusion, then a cross-encoder rerank of the top ~50 down to ~10.
  • Never pick silently. Two currentHeading fields within a close score margin → ask the user, or investigate both inside a bounded budget and report both.

🧠 Remember

  • Exact first, semantic as an add-on, graph for structure.
  • Log templates, config keys and constants are cheap, exact entry points. Index them.

🪪 Identifier grounding

Every code-like token in the prose (PascalCase, snake_case, a.b(), file.cs) must resolve to an indexed symbol or file, or appear in cited evidence. Otherwise it gets flagged and removed. This catches invented method names cheaply, the “naming” hallucinations in the CodeHalu taxonomy.

🔗 Trace continuity

Every consecutive pair in a trace needs a call, flow or hop edge between them. A gap is rendered as ⋯ unverified hop with RUNTIME-DEPENDENT, never smoothed over.

🧾 Prose bound to claims

Each rendered sentence references claim IDs. A sentence with no claim is shown as commentary, visually distinct, and can't introduce a code fact.

♻️ Repair, not retry

The verifier tells the model why a claim failed (“no edge A→C; A→B→C exists”). Two rounds at most, then whatever is still unresolved is shown as such.

Where this idea comes fromAtomic-claim decomposition and verification (FActScore, SAFE), citation precision and recall (ALCE), and validator stages in LLM program analysers (RepoAudit's validator, AEGIS's verifier agent). The difference here is that the checker for code claims is deterministic, because the facts live in a database.
Knowledge check
A test run shows ProcessGpsData was never called while the ground station was idle. The model concludes it “is not called when idle”. What status is right?
Why: runtime can confirm that something happens but can never show that it can't. “Not called when idle” is an impossibility claim, so it needs static reachability analysis under the idle condition, plus a certificate listing unresolved edges.

  • Claims are data. Data can be checked.
  • The weakest edge decides a path's status. A gap is shown, not smoothed over.

A one-line edit must not trigger a re-index of millions of lines. Three ideas make that work. Content-addressed facts (reuse whatever didn't change). Interprocedural value flow and slices; Joern cross-checks; cppcheck ValueFlow per data model; Frama-C Eva where the code parses cleanly; PhASAR where the code builds to bitcode.

MVP definition

The smallest system that shows the core idea (compiler facts + LLM explanation + deterministic verification) on real C and C# code, with zero configuration, on whatever machine it's installed on, and without any runtime machinery yet.

In scope
  • Windows and Linux hosts, x64 (arm64 where the toolchains exist)
  • C with dialect packs neutral, MSVC and GCC/Clang, plus embedded vendor packs as keyword shims; C# from a captured build or ad hoc
  • With or without builds: capture or reconstruct, fidelity F1–F4 on every fact
  • Layers L0–L3, the state graph, free macros and parametric configurations, the data-model sweep, the I/O catalogue with MMIO/ISR patterns
  • Call resolution: direct, CHA/RTA, DI, events, fn-pointer tables, type-based fallback, P/Invoke when present
  • Capability probe + model ladder, C0 through C4, with budgets set from the self-benchmark
  • Six recipes: symbol.explain, calls, usage, reach.conditions, config.impact, change.impact
  • Verifier v1 with fidelity, configuration and data-model qualifiers; absence certificates; OS-level egress block
  • Desktop app with the Ask, Search, Code and Index & jobs views, the live investigation timeline, and budgets met on a 1M-LOC fixture (§11); CLI with --json
  • Benchmark v0: suites S (including no-build repositories), R and U
Out of scope (later phases)
  • Interprocedural slicing beyond the state graph (P4)
  • Execution adapters, harnesses, scenarios and fault injection (P5–P6)
  • Deep analysers and concurrency (P4, P8)
  • Incremental daemon and scale features (P9)
  • macOS adapters and class C5 tuning (P10)

Phase 4: the local model as a judge, meaning search, real C#, and stricter grading (1 Oct 2026, day)

Phase 3 showed where first contact fails: behavioural questions picked the wrong check among thousands. Phase 4 asked whether the local model and meaning search can fix that without letting the model invent anything. The model only chooses, among real candidates the analysis has already found and verified, the one whose code best fits the question. Every candidate is shown to it as the real code (file, line, condition, what the branch does). It cannot add a name, a line or a fact. A changed choice is disclosed in the answer ("the local model chose this check from N candidates…"). Its wording is now a short summary that is always followed by the complete checked facts.

Generalisation was measured as before: each new project's questions were written from its source first, then run once in four modes (keyword only, + meaning search, + local model, + both), and those first runs were kept. Phase 4 also changed how runs are scored. Phase 5 (3 Oct 2026): learning from corrections

The spec is VERITY_LEARNING_FROM_CORRECTIONS_ONE_PAGER.html (d98); its section 08 has the status. Known limitations (not hidden)

Built and verified on macOS only. The primary production target is Windows 10/11 with the MSVC compiler, then GCC and TI. The MSVC and TI dialect packs, vcxproj/CCS flag capture and the Windows paths exist but are untested on Windows. Runtime scenarios need a local C compiler and a sandbox: the Windows Sandbox/TTD adapter is not built, so on Windows today scenarios fall back to static reading (INFERENCE). The desktop bundle is macOS-only; Tauri builds for Windows are possible but not produced. C# questions are answered by reading the code (Roslyn facts); C# scenarios are not run.
  • C data flow is field-based (all instances of a struct share field nodes) with no SSA or general pointer-alias analysis. Claims that pass through struct fields are marked INFERENCE.
  • Configuration variants: the 4 never-defined macros guarding the most code, plus one build with every overridable feature option on. Other combinations are not explored, and the data-model sweep is not implemented.
  • Scenarios: C only. Hardware is replaced by logging stubs, and time is modelled by advancing tick parameters. C# scenarios are not implemented. Nested sandboxing is impossible on macOS, so runs are disabled inside an outer sandbox, and the answer says why.
  • Routing: the router is rule-based with a model fallback. Unusual phrasings can fall back to search; such answers stay grounded, are shown exactly as found, and are never reworded by the model.
  • Behavioural questions on first contact are right about 4 times in 10 without the model and about 6 in 10 with it (final frozen round: 9/24 → 14/24, hand-audited). The misses are domain meaning the code does not spell out: the MQTT SUBACK failure code 0x80, priority inheritance in a mutex, "output buffer" vs "array" in nanopb. A wrong pick is always visible, because the answer names the function and line it chose.
  • The model needs most of a 24 GB machine. Run one Verity engine (app, CLI or MCP) with the 20B model at a time. A second engine that cannot load it answers in facts-only mode and says so. Model answers take a median of 12 s (90% within 24 s); Direct answers under a second.
  • Model summaries are checked for names and quoted code, not for meaning. In the audit, 2 of 64 summaries contradicted the facts printed under them (one added textbook "priority inheritance" to a priority-ceiling mutex). The checked facts are the answer; the summary is a convenience. Meaning search, on by default, also widened one SOEM pool so the model chose a worse check.
  • Scoring: the benchmark's grader checks names, not meaning, so it can pass a wrong branch or a false sentence. Every first run, and the tuned answers of held-outs #5–#9, were also read by hand; older suites were read where the fixes changed them. Grow the benchmark from real users' questions and keep auditing.
  • Validation scale: two samples, a generated 48K-LOC project, two dialect samples and twelve real open-source projects nobody tuned for at first: ten in C (minmea, FreeRTOS, lwIP 173K, libmodbus, littlefs, CANopenNode, SOEM, uC/OS-II, Paho MQTT, nanopb) and two in C# (M2Mqtt, NModbus). Not yet a customer's industrial codebase.
  • Desktop: the native folder-picker permission is proven, but no person has clicked through the dialog; the self-test opens projects directly.

Final readiness assessment

Verdict after Phase 4: ready for pilot use by engineers on real, uncompiled C and C# codebases (tested up to 173K lines) on macOS; not yet production-certified for the Windows/MSVC target.
  • Trustworthy from the start: call paths, what a function does, where a value is set, threads and entry points, and names that do not exist.
  • Behavioural questions ("what happens when it is full / times out / is rejected") are answered with verified facts every time and pick the right check about 6 times in 10 on first contact with the local model. The answer always names the function and line it chose, so a wrong pick is visible.
  • Nothing leaves the machine, every statement is re-checked against the code, scenarios run the real code in a sandbox, and the model can only choose among real code or summarise checked facts.
  • Every surface was tested end to end: the app, the browser UI, the CLI, MCP, an offline install from the bundled packages, and the network check.
  • The narration was audited, not only the facts: 64 tuned answers and 64 model summaries were read against the code; the false connecting sentences that turned up were fixed generically and are covered by regression tests.
Before calling it production-ready:
  1. Run it on Windows with MSVC on 2–3 customer codebases, and grow the benchmark from their questions.
  2. Build and test the Windows runtime adapter.
  3. Add C# scenario execution.
