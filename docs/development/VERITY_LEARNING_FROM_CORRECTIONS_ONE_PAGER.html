Make each project's answers better every time someone corrects them

Today Verity answers the same question the same way until an engineer changes its code. This feature lets the people using it point at the right place when an answer is wrong. The correction is kept for that project, shown in every answer it affects and can be undone. It becomes ranking hints, glossary words and test cases, with no model retraining and nothing leaving the machine.

WHY · 01

Today it never learns

On a project Verity has never seen, structural answers are dependable from the start. Behavioural questions ("what happens when it is full / times out / is rejected") are the weak spot. The people asking often know the right place, but they have no way to tell Verity.

Where accuracy stands (v0.5.0)ResultMeasured on

What the remaining misses look like

Right place, wrong rank

The correct check was a candidate, but another ranked first. Example: SOEM "error list is full", where the index wrap-around beat head == tail. How common this is has not been measured; that is P5-0.

Meaning the code does not spell out

MQTT's SUBACK failure code 0x80, a priority ceiling mistaken for priority inheritance, the word "bus-off". A project glossary fixes these.

Code the default build leaves out

nanopb's nesting limit sits behind #ifdef PB_MESSAGE_NESTING_MAX. A correction can point at it; a real Windows build removes the guess.

Paths the analysis does not follow

A timeout caught inside an #if DEBUG … #else pair of handlers (M2Mqtt Ping()). Ranking cannot fix this; the correction flags it for the engineering loop.

The ideaLet the person who knows say so once, and make every later answer on that project use it: openly, reversibly, and without inventing anything.
Measure this firstNobody knows yet how often the right check is already among the top 3 candidates. That number decides how much "show the alternatives" is worth (step P5-0).

What stays human: the engineering loop

Corrections make one project better. Making every project better is still engineering, done the same way as the Phase 4 audit:

Collect

Export corrections from the pilot projects (corrections.export).

Sort

Rank problem (the right check was a candidate), vocabulary (a glossary would do), or analysis gap (the path is not followed at all).

Fix generically

One rule plus a regression test per idiom, never a special case for one project.

Re-measure

On a never-seen project: questions written first, first run kept, read by hand.

STORAGE · 04

Kept apart from the index

The index can always be rebuilt from the code; corrections cannot. So they get their own file in the same project folder.

index.db (exists)
  • Rebuildable. A corrupted one is moved aside and recreated (verity/store/db.py:109).
  • Already keeps every answer with an id and the hashes of the files it used (answer table, db.py:64, written by Answerer._store, verity/agent/answer.py:278).
learned.db (new)
  • data/repos/<repo-id>/learned.db, next to the index (config.repo_dir).
  • Survives re-index, full re-index and index corruption. A correction refers to the answer it fixes by id.
learned.db, proposed schema
CREATE TABLE correction (
  id TEXT PRIMARY KEY,                 -- c-0007
  created REAL, author TEXT, note TEXT,
  answer_id TEXT,                      -- answer.id in index.db
  question TEXT, intent TEXT, topic TEXT,          -- topic = the router's words (JSON list)
  wrong TEXT,                          -- JSON {fn, file, line, cond} that ranked first
  target_fn TEXT, target_file TEXT, target_line INT, target_cond TEXT,
  anchor TEXT,                         -- sha1 of the target line's code text
  status TEXT                          -- active | stale | removed
);
CREATE TABLE glossary (term TEXT, identifiers TEXT,  -- "bus-off" -> ["CO_CAN_ERRTX_BUS_OFF"]
                       source TEXT,                 -- correction id or "manual"
                       status TEXT);                -- suggested | accepted | rejected
CREATE TABLE confirmation (answer_id TEXT, created REAL, question TEXT);  -- "the answer was right"
When the code changesEach correction stores the target line's text hash and its function. After every index it is re-anchored. If the line moved, it follows it inside the same function. If the code on that line changed or disappeared, the correction turns stale: it is listed for review and never applied.
Sharing with a team. Corrections stay on the machine. To share them, export and import a JSON file. Accepted glossary terms can also be committed to the repository's existing verity.toml, the hints file read by config.load_hints (verity/config.py:37), under a new [glossary] table.

GUARDRAILS · 05

What it does on its own, and what it never does

"Auto-improvement" here means: once someone corrects an answer, the rest happens by itself, inside that project, in plain view.

Automatic, after a correction
  • Saved and used at once, for this project
  • Pins the same question; nudges similar ones
  • Suggests glossary words
  • Adds a test case
  • Turns stale by itself when the code changes
Never automatic
  • Deciding that an answer is wrong (a person flags it)
  • Accepting a glossary term
  • Applying to another project
  • Turning corrections into general rules (engineering: reviewed, tested, measured)
  • Retraining the model, or sending anything off the machine
  • A correction only reorders candidates, or builds one from real code. Every claim still passes the verifier.
  • Every answer that uses a correction says so, with its date and note. One click undoes it.
  • A picked line must exist in the indexed project. A pick from the alternatives must be one of them.
  • When two corrections disagree on the same question, the newest wins and both are flagged.
  • Works in facts-only mode too. The model is not needed.
Not thisSilently tuning weights from thumbs-down clicks. Unreviewed feedback drifts towards confident wrong answers, and nobody can tell why an answer changed.

P5-2 · Correction store and interfaces (≈1–1½ days)

learned.db, plus the RPC methods, verity correct / verity corrections, and the MCP verity_correct tool.

P5-3 · Apply: pin, hint, glossary (≈1½ days)

Load matching corrections once per question. Pin, or add the hint bonus inside each recipe's ranking. Per-project glossary on top of the global word map. Disclosure line in the answer.

P5-4 · Anchors and stale corrections (≈½ day)

Re-anchor after each index; stale corrections are never applied.

P5-5 · App (≈1 day)

Buttons on the answer card, "use this line" in the source viewer, and Settings → Corrections / Glossary (undo, accept, export).

Acceptance

  • The corrected question asked again: right every time, with the correction disclosed.
  • A paraphrase of a corrected question (written beforehand): right in at least 9 of 10.
  • A neighbouring question in the same area: reported honestly, with no target.
  • Unrelated questions and every existing suite, facts-only and with the model: no score drops, and changed answers read by hand.
  • A target line edited or deleted, then re-indexed: the correction is never applied and is listed as stale.
  • learned.db survives an index.db reset.
Keep the two numbers apartReport accuracy before any correction (first contact, as today) and after one correction per miss. Never blend them: the second measures the team's effort, not the tool's first impression.

Quick answers

Does it retrain the model?

No. The model's weights never change; corrections steer which verified candidate comes first.

Does it need the model?

No. Pin, hints and glossary work in facts-only mode too.

Does one project affect another?

Not automatically. Only by export and import, or through the repository's verity.toml.

What if a correction is wrong?

Every answer that uses it says so, and one click undoes it. Stale and conflicting corrections are never applied silently.

Who can see corrections?

Only this machine, unless someone exports them.

Does it fix analysis gaps?

No. Those become flagged cases for the engineering loop.
